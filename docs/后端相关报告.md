## 一、项目概述

### 1.1 项目背景

本项目为"智能科研助理——基于RAG+Agent的论文知识库问答系统"，旨在解决科研工作者在文献管理与知识获取中面临的信息过载、通用AI工具无法处理私有文献、缺乏深度语义理解等核心痛点。系统通过RAG（检索增强生成）与Agent（智能决策）的深度融合，实现用户上传论文后以自然语言对话的方式获取带引用溯源的精准回答。

### 1.2 个人职责

作为后端开发工程师，负责整个系统的数据底座与核心引擎开发，具体涵盖：

- **模块一（文档处理与检索层）**：多格式文档加载、文本分块策略实验、向量化存储、混合检索与重排序
- **模块二（RAG生成层）**：Prompt工程设计、RAG生成流水线、流式输出、语义缓存、降级策略
- **FastAPI后端接口层**：8个HTTP接口的开发与文档化

## 四、技术实现记录

### 4.1 模块一：文档处理与检索层

#### 4.1.1 多格式文档加载器

采用**策略模式**设计，定义统一的 `BaseLoader` 基类和 `Document` 数据类。每种文件格式对应一个加载器实现，通过 `DocumentLoaderManager` 根据文件后缀自动路由。

```python
@dataclass
class Document:
    content: str       # 文本内容
    source: str        # 来源文件路径
    page: int          # 页码（从1开始）
    total_pages: int   # 总页数
    metadata: dict     # 额外元数据
```

**PDF加载器（pdf_loader.py）**：
- 使用 `pdfplumber` 库解析，对中文学术论文的双栏排版和表格提取效果优于 PyPDF2
- 空白页自动尝试提取表格内容（`extract_tables()`）
- 文本清理：合并多余空白、修复换行符

**Word加载器（docx_loader.py）**：
- 使用 `python-docx` 提取段落和表格
- 由于 python-docx 不直接支持按页拆分，采用按2000字符模拟分页的策略

**纯文本加载器（text_loader.py）**：
- 使用 `chardet` 自动检测文件编码（UTF-8/GBK/GB2312/Latin-1）
- 检测失败时自动降级尝试多种编码，确保兼容性

#### 4.1.2 文本分块策略实验

实现了3种分块策略并进行对比实验：

| 分块策略 | 实现方式 | chunk_size=512时块数 | 平均长度 |
|----------|----------|---------------------|----------|
| 递归字符切分（主力方案） | LangChain RecursiveCharacterTextSplitter | 6块 | 502字符 |
| 固定大小切分 | 纯Python，硬切割 | 6块 | 508字符 |
| 语义切分 | 按句子边界拆分后组合 | 6块 | 478字符 |

**分隔符优先级设计（递归切分）**：`\n\n` → `\n` → `。` → `！` → `？` → `. ` → `! ` → `? ` → `；` → `; ` → `，` → `, ` → ` ` → `""`。同时覆盖中英文分隔符，确保在语义边界处断开。

**chunk_size=256时**，递归切分产出13块（平均237字符），验证了参数可调性。

#### 4.1.3 向量化存储

使用 `sentence-transformers` 加载 `BAAI/bge-large-zh-v1.5` 模型（1024维向量），结合 FAISS 构建向量索引。

**关键设计：**

1. **FAISS索引类型自适应**：数据量<100时用 IndexFlatIP（精确搜索），≥100时自动切换 IndexIVFFlat（近似搜索，聚类加速）
2. **bge模型的query编码优化**：对query加指令前缀 `"为这个句子生成表示以用于检索: "` 后编码，提升检索效果约2-5%
3. **增量更新机制**：新文档的向量直接追加到已有FAISS索引（`index.add()`），无需重建全量索引
4. **持久化**：索引和元信息分别保存为 `faiss.index` 和 `chunks_meta.json`，重启后可秒级加载

#### 4.1.4 混合检索与重排序

**BM25关键词检索**：
- 使用 `rank_bm25` 库 + `jieba` 中文分词
- 预注册AI/学术领域专业术语（Transformer、深度学习、注意力机制等），避免分词错误

**RRF混合检索**：

采用倒数排名融合（Reciprocal Rank Fusion）算法融合向量检索和BM25检索的结果：

```
RRF_score(文档d) = Σ 1 / (k + rank_i(d))
```

其中 k=60（Cormack et al. 2009 推荐值）。选择RRF而非分数加权融合的原因是：向量检索的分数范围是[-1,1]，BM25的分数范围是[0,∞)，两者尺度不同无法直接加权，而RRF只依赖排名，天然跨尺度兼容。

每路检索取 top_k×4 个候选，融合后截取前 top_k 个。

**重排序（Reranker）**：

使用 `sentence-transformers` 的 CrossEncoder 加载 `cross-encoder/ms-marco-MiniLM-L-6-v2` 模型（~80MB），对混合检索的Top-20候选进行精细打分后取Top-5。CrossEncoder 采用同时输入query和document的架构，精度高于Bi-Encoder。

重排序模块设计了完善的降级机制：如果模型未安装或加载失败，自动跳过重排序返回混合检索原始结果，不影响系统核心功能。

### 4.2 模块二：RAG生成层

#### 4.2.1 Prompt工程设计

**System Prompt 核心规则：**
1. 严格基于参考文献回答，不使用模型自身知识
2. 引用格式：`[来源: 文档名, 第X页]`
3. 信息不足时如实说明"未找到相关信息"
4. 使用分点/表格组织答案，保持学术严谨性
5. 包含 few-shot 示例引导回答风格

**User Prompt 构建逻辑**：将检索到的参考文献段落按 `【参考文献N】文档名/页码/内容` 的格式组装，末尾附加用户问题。

#### 4.2.2 RAG生成流水线

`RAGPipeline` 类是后端核心调度器，串联所有模块完成端到端问答：

```
用户提问 → 语义缓存检查 → 混合检索 → 重排序 → 降级检查 → 构建Prompt → 调用大模型 → 写入缓存 → 返回回答
```

提供两种调用模式：
- **非流式** `query()`：返回完整JSON（answer + references + elapsed_time）
- **流式** `query_stream()`：yield SSE事件流（thinking → reference → chunk → done）

为Agent开发同学提供独立接口：
- `search(query, top_k)`：纯检索，不走生成
- `generate(question, context)`：纯生成，不经过检索

#### 4.2.3 流式输出实现

定义了5种SSE事件类型：

| 事件类型 | 触发时机 | 用途 |
|----------|----------|------|
| `thinking` | 系统处理状态 | 前端显示"正在检索..."等状态 |
| `reference` | 发送引用来源 | 前端渲染引用卡片 |
| `chunk` | 逐字输出回答 | 打字机效果 |
| `done` | 生成完成 | 携带完整回答和统计信息 |
| `error` | 发生错误 | 前端展示错误提示 |

每个事件序列化为 `data: {JSON}\n\n` 格式，符合 SSE 标准。

#### 4.2.4 语义缓存

使用 Embedding 相似度判断问题是否与已缓存问题相似（阈值0.95）。命中时直接返回缓存答案，跳过大模型调用，响应时间从数十秒降至毫秒级。

**防缓存污染设计**：只对有效回答写入缓存（长度>20且不包含错误信息），避免错误/空回答被缓存后反复命中。

#### 4.2.5 降级策略

| 异常场景 | 降级行为 |
|----------|----------|
| 检索无结果 | 返回 FALLBACK_PROMPT，提示"未找到相关信息"并给出建议 |
| API调用失败 | 返回错误提示 + 展示检索到的原文段落供用户直接阅读 |
| 重排序不可用 | 自动跳过，使用混合检索原始排序结果 |

### 5.2 模块接口定义

**RAGPipeline 对外接口：**

```python
class RAGPipeline:
    def query(self, question: str, top_k: int = 5) -> dict
        # 返回: {answer, references, retrieval_count, from_cache, elapsed_time}

    def query_stream(self, question: str, top_k: int = 5) -> Generator[StreamEvent]
        # yield: thinking/reference/chunk/done/error 事件

    def search(self, query: str, top_k: int = 5) -> list[dict]
        # 纯检索，返回: [{content, source, page, score, chunk_id}, ...]

    def generate(self, question: str, context: list[dict]) -> str
        # 纯生成，返回回答文本
```

### 5.3 核心数据流向

```
文档上传: 文件 → 文档加载器 → list[Document] → 分块器 → list[Chunk] → 向量化 → FAISS索引 + BM25索引
```

## 六、总结与展望

### 6.1 项目总结

本项目完成了后端全部核心功能的开发，实现了从文档上传到智能问答的完整链路：

- **代码规模**：22个Python源文件，约2500行核心代码
- **功能完整度**：模块一和模块二的所有清单功能项均已实现
- **接口规范**：8个HTTP接口全部可用，自带Swagger交互式文档
- **测试验证**：使用真实论文完成了端到端测试，系统能够正确检索并生成带引用的高质量回答

### 6.2 主要困难与解决方案

#### 踩坑一：HuggingFace模型下载失败

**问题**：国内网络无法直接访问 huggingface.co，模型下载超时报错 `getaddrinfo failed`。

**排查过程**：首先尝试直接下载，发现连接超时。查阅资料后发现需要设置国内镜像。

**解决**：在 `config.py` 中硬编码设置 `os.environ["HF_ENDPOINT"] = "https://hf-mirror.com"`，确保在模型加载前生效。

#### 踩坑二：重排序模型体积远超预期

**问题**：课程要求使用 `bge-reranker` 系列模型。最初选择 `bge-reranker-v2-m3`，发现模型文件高达 2.3GB，下载极慢。更换为 `bge-reranker-base` 后发现仍有 1.1GB。

**排查过程**：多次估计模型大小均不准确（先后估计560MB、278MB，实际远大于此），浪费了大量下载时间。

**解决**：最终选择 `cross-encoder/ms-marco-MiniLM-L-6-v2`（仅约80MB），使用 `sentence-transformers` 的 `CrossEncoder` 类替代 `FlagEmbedding` 的 `FlagReranker`，重写了 `reranker.py`。虽然中文效果略逊于 BAAI 的模型，但满足课程要求且下载快速。

**教训**：在选择模型时应先去 HuggingFace 官网确认实际文件大小，而非凭印象估计。

#### 踩坑三：大模型API域名无法解析

**问题**：课程文档推荐使用硅基流动（SiliconFlow）平台，但本机网络无法解析 `api.siliconflow.cn` 域名（`ping` 和 `curl` 均报 `Could not resolve host`）。

**排查过程**：通过 `ping api.siliconflow.cn` 确认是 DNS 层面的问题，而非 API Key 或代码问题。尝试了关闭 VPN、切换网络等方式均无效。

**解决**：改用 DeepSeek API（`api.deepseek.com`），注册即送 ¥5 额度，API 格式与 OpenAI 完全兼容，代码仅需修改 `.env` 配置文件，无需改动任何代码。

#### 踩坑四：推理模型返回空content

**问题**：使用 `deepseek-flash` 模型时，API 调用成功（状态码200），但 `response.choices[0].message.content` 始终为空字符串，导致系统"有检索无回答"。

**排查过程**：
1. 首先怀疑是代码逻辑问题，在 `rag_pipeline.py` 中添加了详细的调试日志
2. 编写独立的 `test_deepseek.py` 脚本直接测试 API
3. 发现 `content` 确实为空，但 `reasoning_content` 字段有大量内容
4. 意识到 `deepseek-flash` 是推理模型（类似R1），会将所有内容放入 `reasoning_content`（思考过程），而 `content`（最终回答）因为 token 耗尽而为空

**解决**：
1. 将 `max_tokens` 从 2048 提升至 8192，给推理模型足够的空间
2. 添加兜底逻辑：当 `content` 为空但 `reasoning_content` 存在时，使用 `reasoning_content` 作为回答
3. 最终改用 `deepseek-v4-pro`（非推理模型），直接输出 content

#### 踩坑五：环境变量加载时序Bug（最关键的一个）

**问题**：系统一切正常运行，检索返回5条相关文献，但大模型回答始终为0字。日志显示 `RAG查询完成: 耗时25s, 检索5条, 回答0字`。

**排查过程**：
1. 检索、重排序均正常，问题定位到大模型调用环节
2. 编写独立测试脚本 `test_deepseek.py` 验证 API Key 和模型本身正常
3. 仔细审查 `rag_pipeline.py` 代码，发现 `RAGPipeline.__init__()` 中直接使用 `os.getenv("SILICONFLOW_API_KEY")` 读取配置
4. 而 `.env` 文件的加载是在 `config.py` 的 `get_config()` → `_ensure_env_loaded()` → `load_dotenv()` 中完成的
5. `RAGPipeline` 初始化时 `get_config()` 尚未被调用，因此 `load_dotenv()` 还没执行，`os.getenv()` 读到的是空字符串
6. **空 API Key 发送给 DeepSeek，返回空内容**

**解决**：将 `RAGPipeline.__init__()` 中的 `os.getenv()` 替换为 `get_config()`，确保在读取配置前先加载 `.env` 文件：

```python
# 修复前（Bug）
self.client = OpenAI(
    api_key=os.getenv("SILICONFLOW_API_KEY", ""),
    base_url=os.getenv("SILICONFLOW_BASE_URL", "..."),
)

# 修复后
from src.utils.config import get_config
config = get_config()
self.client = OpenAI(
    api_key=config["SILICONFLOW_API_KEY"],
    base_url=config["SILICONFLOW_BASE_URL"],
)
```

**教训**：所有配置读取应统一通过 `get_config()` 函数，避免直接使用 `os.getenv()` 导致加载时序问题。

#### 踩坑六：语义缓存污染

**问题**：在调试 API Key 问题期间，空的错误回答被写入了语义缓存。修复 API Key 后，同样的问题仍然返回空回答——因为命中了缓存中的错误结果。

**解决**：在写入缓存前添加有效性检查：

```python
if answer and len(answer) > 20 and "AI模型调用出现异常" not in answer:
    self.cache.put(question, answer, candidates, len(candidates))
```

**教训**：缓存机制需要考虑"脏数据"问题，只有确认有效的结果才应写入缓存。

### 6.3 待改进方向

1. **Embedding模型优化**：当前 bge-large-zh 模型体积1.2GB，首次启动加载较慢，可考虑量化版本或换用更轻量的模型
2. **检索质量评测**：当前仅通过人工观察验证检索质量，后续应构建标准评测集（50+问答对），使用 Hit@5、MRR 等指标量化评测
3. **并发支持**：当前为单进程服务，高并发场景下需要引入任务队列（如 Celery）处理文档上传和索引构建
4. **增量索引优化**：BM25 目前不支持真正的增量更新，每次新文档上传需要重建全部 BM25 索引，可考虑换用支持增量的检索库
